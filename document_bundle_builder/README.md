# Document Bundle Builder V1

Изолированная офлайн-упаковка подготовленных семи слоёв одного документа. Builder не извлекает PDF, не вызывает модели, не строит индексы и не подключает результат к RAG. Идентификаторы двигателя/чанков и число записей не зашиты в алгоритме.

## Входной контракт

Путь `--input` содержит `source.pdf` и `prepared/`: `source_map.sqlite`, `text_chunks.sqlite`, `table_layer.sqlite`, `figure_layer.sqlite`, `text_table_links.sqlite`, `text_figure_links.sqlite`, `passport_layer.sqlite`, каталоги `assets/`, `metadata/`, `evaluation/`. В `metadata/prepared_file_registry.json` находятся относительные пути от входного корня и SHA-256 ранее подготовленных файлов; отсутствие или несовпадение файла останавливает сборку. Остальные файлы трёх каталогов также включаются в хеш идентичности и пакет. Входные SQLite должны иметь физические таблицы и поля существующих семи этапов, используемые в `inspect()`; другие схемы автоматически не поддерживаются. `--document-id` сверяется с source map и всеми присутствующими полями document_id.

Сборщик параметризован документом, но пока проверен только на одном реальном комплекте с конкретной схемой Stage 01–07. Для иных форматов слоёв нужен проверенный согласованный адаптер; совместимость остальных пяти PDF не доказана. `inputs/ARCHITECTURE.md` внутри архива Stage 07 — обнаруженный архитектурный handoff; отдельный `KAMAZ_KB_ASSEMBLY_SPEC_V1_1.md` в репозитории не найден.

## Схема knowledge.sqlite

Все обычные таблицы исходных семи SQLite сохраняются без фильтрации строк и колонок как `<имя_слоя>__<исходное_имя_таблицы>`, например `text_chunks__chunks`, `table_layer__table_chunks`, `passport_layer__anchors`, `text_table_links__semantic_links`. Значения, типы SQLite, порядок колонок и исходные ID проверяются каноническим логическим SHA каждой таблицы и числом строк. Исходные SQL-определения таблиц и эти SHA хранятся в `bundle_source_schema(layer,source_name,output_name,source_ddl,row_count,logical_sha256)`. Физические ограничения/индексы/триггеры на копии не создаются: их исходный DDL не следует путать с действующими ограничениями новой БД; они не реконструируются автоматически. Архивный пакет пригоден только для чтения.

`bundle_search_records(kind,source_id,document_id,search_text,search_sha256,pages_json,engine_ids_json,scope_conditions_json,future_candidate,runtime_enabled,source_layer)` — механическая проекция существующих text/R6/R4 полей. SHA относится ровно к сохранённому `search_text` UTF-8. Это не утверждённый полный input embedding, если будущий процесс потребует контекст или иное представление. Заблокированные объекты и обособленные таблицы не исключаются. Ссылки source refs, таблицы, рисунки, условия, блокировки и доказательства доступны в исходных таблицах с префиксами; формат `{kind,id}` не меняется. Семантическая корректность и runtime-допуск не выводятся из факта сборки.

## Запуск

Из корня проекта (PowerShell):

```powershell
$env:PYTHONDONTWRITEBYTECODE='1'
python -m document_bundle_builder.builder --input kb_sources/DOC-YAMZ-236M2-01 --output document_bundles --document-id DOC-YAMZ-236M2-01
python -m unittest document_bundle_builder.test_builder -v
```

Для следующего документа подставить другой входной корень и его точный document_id после подготовки полного совместимого комплекта и реестра. Исходные архивы сохраняются в исходном каталоге; в Bundle входят PDF, assets, metadata, evaluation, knowledge.sqlite, manifest.json и validation_report.json.

ID — SHA-256 от версии и SHA реализации Builder, document_id и SHA всех входных файлов. Сначала данные пишутся во временную директорию в том же output, проверяются и переименовываются в `build_<id>`. При повторной сборке проверяются совпадение манифеста/отчёта, логического содержимого таблиц и ресурсов; существующая директория не перезаписывается. Байтовая идентичность SQLite не обещана.

## Ограничения и проверки

Достоверность реестра не означает авторитетность технического содержания: `independent_semantic_audit=false`, кандидаты не являются runtime-разрешением. У 19 регионов отсутствует source_object_id; у одного различается fingerprint: эти объекты и исходные поля сохранены, в validation_report перечислены IDs. Исторические незавершённые пути отражены индивидуально как `unresolved_historical_reference` / `unknown_not_assumed_required`: без достаточных доказательств Builder не объявляет их ни обязательными runtime-файлами, ни безопасными для исключения. Адресные блокировки по зависимости от единственного отсутствующего источника автоматически не устанавливаются: правила доказательства зависимости в источниках не формализованы, необходим отдельный аудит. Runtime отключён для Bundle в целом; индивидуальные исходные статусы не повышаются.

Системы индексирования и engine applicability, независимая проверка источников, дополнительные действия по данным и устранение предупреждений — отдельные этапы. При передаче Bundle сохранить исходные ZIP и при необходимости получить отсутствующие исторические crop/растры; не выдавать механическую валидацию за техническую экспертизу.
