# KB Assembler V2 — механическое объединение

V1 (`assembler.py`, `README.md` и сборка V1) сохранён без изменений. V2 находится в `assembler_v2.py` и не использует его логику смыслового допуска. Из V1 импортируются только технические функции проверки Bundle, безопасной работы с путями и формата данных. V2 не строит индексы и не включает runtime.

Из корня проекта:

```powershell
$env:PYTHONDONTWRITEBYTECODE='1'
python -m kb_assembler.assembler_v2 --config kb_assembler/yamz236_config_v2.json
python -m unittest kb_assembler.test_assembler_v2 -v
```

Конфигурация содержит engine_id, список путей версионированных Bundle, output и schema_version. Состав документов задаётся только конфигурацией; пути входов разрешаются относительно текущего каталога. Для добавления второго документа достаточно добавить его Bundle в список и повторить команду. Сортировка по document_id делает порядок списка несущественным.

## Схема Engine KB

Каждая таблица исходного `knowledge.sqlite` переносится целиком под тем же именем и с теми же колонками; добавлена только техническая колонка `bundle_document_id`. Это составной идентификатор документа для объединения двух файлов с одинаковыми локальными ID, а не замена исходных ID. Имена и типы исходных колонок всех Bundle должны совпадать, иначе сборка отклоняется. Для каждой таблицы каждого документа проверяются количество и логический SHA всех исходных значений; соответствующие записи находятся в `validation_report.json`. Физические SQLite-ограничения/индексы, которых уже нет в Bundle V1, V2 не реконструирует.

В `search/search_inputs.json` представлены **все** исходные `bundle_search_records`: 148 text → две проекции, 406 table → table_dense и 154 passport → passport_dense для первого документа. `future_candidate`, `runtime_enabled`, статусы и условия сохраняются; они не оцениваются сборщиком. Проекции — исходные данные, а не разрешённый рабочий индекс: downstream-компонент должен применять исходные ограничения. `search/index_manifest.json` явно отмечает отсутствие BM25 и векторов. Механического объединения недостаточно, чтобы подтверждать применимость любых записей к двигателю.

`resolve(kb_root,engine_id,document_id,kind,source_id)` требует document_id при разрешении источника: возвращает оригинальный PDF и физические страницы; для figure_id — все PNG-регионы с проверкой SHA. Он разрешает ресурс для проверки происхождения, но не выдаёт разрешение на рабочий показ или использование содержимого. PDF, PNG, исходные metadata и evaluation копируются по относительным путям `sources/<document_id>/`; их SHA сохраняются в манифесте.

Входной Bundle проверяется по манифесту, логическим хешам и SHA ресурсов; межслойные ссылки и страницы проверяются технически. При сбое staging не публикуется. ID зависит от версии и SHA кода, schema_version, engine_id и идентификаторов/хешей входных Bundle. Сборка в staging публикуется переименованием, существующие версии не удаляются; повторная сборка сверяет манифест, логическое содержимое и ресурсы. Для различных схем семи слоёв требуется отдельная согласованная адаптация: V2 не угадывает соответствие столбцов.

Для следующего этапа остаются применение исходных условий и блокировок в рабочем поиске, независимая оценка доказательств, эмбеддинги и индексы, адаптер к RAG. Они в V2 не реализованы.
